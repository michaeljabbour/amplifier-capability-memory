# Existing stores and export boundaries

The portable Memory method installs independently. Its native execution backend uses the separately owned amplifier-data foundation. The reviewed code-only Data distribution is public at [amplifier-tool-data](https://github.com/michaeljabbour/amplifier-tool-data); the original private repository and history remain private. No old store is discovered, opened or converted by installing the method.

| Store | Existing format/location | Supported transition in this release |
|---|---|---|
| Project Memory bundle | SQLite at a project's `.amplifier/project-memory/memory.db`, with `memories`, `raw_captures` and `schema_meta` | Explicit schema-1 archive export and new-log archival import; no semantic/behavioral conversion. Keep the original database and source history. |
| Standalone tool-memory 0.1.x | SQLite, normally `~/.amplifier/memories.db`, with observations and session/file context | No full-fidelity adapter is shipped. Historical documentation does not establish that an installed export exists or covers related tables. |
| Former vendor-backed Memory | The source and destination configured for that historical version | The former one-time importer and migration extra were removed. Historical release notes describe history, not a currently installed command. |
| Current native Memory | An explicitly selected amplifier-data append-only log | Preserve the original log for replay/regeneration. An evidence view is useful for inspection but cannot replace the log. |

Before any requested migration, identify the actual format, schema/version, configured path, writer processes, source revision and destination. Work on a consistent backup; a SQLite store in WAL mode can have uncheckpointed state outside its main file. Do not delete journals or copy only the main file while a writer is active. The schema-1 archive bridge preserves all three tables and rejects unknown/missing columns or changed snapshots. Other adapters must prove counts, exact content, identifiers, timestamps, explicit/observed provenance, unprocessed captures and scope mappings, with rejected or unmapped fields reported. It must preserve the source and provide rollback. These are acceptance requirements, not a claim that such an adapter exists.

Do not use the old Project Memory `MemoryStore` constructor as a supposedly read-only reader: it initializes schema and WAL mode, and some read methods update access counters. A reviewed exporter would need an explicit read-only SQLite connection against a consistent copy. No user store was opened while preparing this release guidance.

The supported `memory-evidence --store PATH export --wing WING [--room ROOM]` emits `memory-evidence-view/1`. It returns at most 10,000 drawers within the selected scope. It is not a full-fidelity native log backup, a complete graph/event export, a legacy SQLite reader, or proof that all data was transferred. Keep the source log and verify any destination separately. Search/export use `record_access=False`; that alone is not an immutable-storage or physical-deletion guarantee.

Do not retire old storage code merely because the new method is published. Retirement requires an independently installable native path, an identified consumer/store inventory, a tested applicable export/import path and a retained rollback. The old Project Memory source remains available read-only in its archived repository; archiving its code does not migrate or delete any installed store. A user migration still requires an explicit source/destination decision.

## Explicit Project Memory schema-1 bridge

See the [portable bridge instructions](../skills/memory/references/legacy-archive.md) and `skills/memory/scripts/legacy_sqlite_archive.py`. Export is stdlib-only, opens only a temporary DB/WAL copy with SQLite mode=ro, and checks DB/WAL/SHM hashes and stat before/copied/after observations. It rejects a detected live-writer change rather than publishing an unstable archive. Quiesce writers/readers first; these checks do not lock out a writer or establish a filesystem snapshot after the final observation.

The versioned artifact preserves all rows/columns/types in `memories`, `raw_captures` and `schema_meta`. Binary values use base64, null stays null, integers use exact decimal strings and real values use hexadecimal float strings. The tested export includes more than 10,000 captures; it does not use the bounded evidence-view API. The 64 MB DB/WAL/SHM input and 128 MB artifact caps reject larger inputs without partial export. FTS/indexes and SQLite internals are outside the three-table archive: keep a full consistent original backup too.

Import requires existing native Memory/Data packages and an explicit new log plus `legacy-archive/<name>` scope. It validates the entire artifact before constructing a store, files a manifest and typed source rows as archival evidence, disables passage derivation for these opaque payloads, closes/reopens the native log and byte-checks payloads before exclusive publication. It never appends to an existing store, promotes old decisions into adopted facts, applies old decay/forget behavior or makes Data public. Eight fictional-fixture tests passed, including source DB/WAL/SHM byte equality, changed-writer/schema/malformed-artifact rejection, 10,005 capture preservation and a separate-process native durable roundtrip on the reviewed Data wheel. This is a bounded archival-transfer gate, not an actual user migration or usefulness result.
